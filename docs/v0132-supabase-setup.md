# V0.13.2 — mise en service Supabase (à faire par le propriétaire)

État confirmé par le propriétaire au début de V0.13.3 : la migration V0.13.2 est appliquée au projet réel et la fonction `duel` a été déployée manuellement. Codex n'a effectué aucune opération Supabase distante. Voir `docs/v0133-security-checklist.md` pour les changements locaux V0.13.3 qui restent à appliquer.

1. Vérifier que la migration V0.13.1 `202610040001_v0131_accounts_cloud_save.sql` est déjà appliquée. Dans Supabase SQL Editor, exécuter ensuite le contenu exact de `supabase/migrations/202610040002_v0132_duel.sql` **une seule fois**. Elle crée `duel_players`, `duel_matches`, les RPC service-role et initialise les comptes existants à 0 point / 10 charges. Ne pas rejouer V0.13.1.
2. Régénérer le module partagé avec `pnpm run build:duel-edge`. Il produit `supabase/functions/duel/engine.js` depuis `src/duelRules.ts`, qui utilise le moteur canonique `src/game.ts`. Garder ce fichier à côté de `index.ts` lors du déploiement.
3. Déployer **uniquement** `supabase/functions/duel/` avec la méthode habituelle du projet (CLI ou Dashboard). Dans le projet réel, la vérification JWT legacy de la plateforme a été désactivée manuellement car incompatible avec la clé publishable utilisée ; le code exige et valide lui-même le bearer via `auth.getUser(token)`. Ne pas retirer cette vérification applicative.
4. Vérifier dans l'environnement sécurisé de l'Edge Function `SUPABASE_URL`, une clé publique (`SUPABASE_ANON_KEY` ou `SUPABASE_PUBLISHABLE_KEY`) et une clé privilégiée (`SUPABASE_SERVICE_ROLE_KEY` ou `SUPABASE_SECRET_KEY`). Ces clés ne doivent jamais aller dans `VITE_*`, dans le navigateur ou dans Git. Les projets Supabase hébergés fournissent généralement les variables de base ; contrôler la configuration effective avant déploiement.
5. Tester avec **deux vrais comptes confirmés**, chacun ayant un Warrior actif et une cloud save synchronisée. Dans Duel > Combattre, vérifier l'adversaire attribué, la persistance après refresh, la consommation d'une charge et le replay. Vérifier Classement, profil et historique initié. `?duelPreview` est un raccourci vers le véritable Duel du compte connecté. Pour une QA visuelle **sans accès Supabase**, `?admin&duelPreview` montre des données factices explicitement étiquetées, et `?admin&duelReplayPreview&qaHold` montre un replay local Karg/Naya ; ces outils n'écrivent aucun joueur dans Supabase.

Sécurité : les tables Duel n'accordent aucun droit direct à `authenticated` ; les RPC sont accordés uniquement à `service_role`. L'Edge Function déduit l'attaquant du JWT et génère le seed elle-même. Le règlement SQL verrouille les lignes, compare les révisions des **deux** saves, ne consomme qu'une charge et garde une réponse idempotente par `(attacker_id, request_id)`.

Classement : points décroissants ; en cas d'égalité, `duel_players.created_at` croissant puis `user_id` croissant pour un ordre déterministe. Aucun point de départ artificiel, aucune saison ni réinitialisation hebdomadaire.

Limite V0.13.2/V0.13.3 : la cloud save solo reste partiellement client-driven. V0.13.3 refuse les structures impossibles avant le Duel, mais un client déterminé peut encore falsifier une possession ou une progression valide en forme via `save_game`. Le résultat, les charges et les points compétitifs sont côté serveur ; les récompenses Duel (100 XP/50 pièces victoire, 25 XP/10 pièces défaite) restent provisoires avant V0.14.

Les tests locaux ne prouvent pas à eux seuls la transaction PostgreSQL réelle ni l'exécution Deno déployée. Le propriétaire a validé la réponse du backend avec un compte ; le scénario deux vrais comptes reste en attente d'un second joueur naturel.
